### RGFW 실패 상세

```
Failed to create a pixel format for WGL.
Failed to set the WGL pixel format.
WARNING: GLAD: Cannot load OpenGL extensions
wine: Unhandled page fault on execute access to 0000000000000000
```

RGFW가 **WGL 픽셀 포맷 선택에 실패** → GL 컨텍스트가 안 만들어짐 → GLAD가 함수 포인터를
못 채움 → 널 포인터 호출로 **즉시 크래시**. GL1.1 구성은 크래시까지는 안 가지만
텍스처·FBO가 전부 실패해서 **화면에 아무것도 못 그린다.**

> ⚠️ **주의: 이 실패가 Wine 고유 문제일 가능성은 있다.** Wine의 WGL 구현은 실제 Windows와
> 다르고, RGFW가 요구하는 픽셀 포맷 속성을 Wine이 지원하지 못했을 수 있다.
> **실제 Windows에서는 동작할 수도 있다.** 하지만 검증할 수단이 없는 상태에서
> 28일짜리 일정을 미검증 백엔드에 걸 이유가 없다.

셰이더 컴파일, 텍스처 업로드, **FBO(렌더 타깃) 생성**, 폰트, WAV 로딩까지 전부 확인.

### 검증 방법 (재현)

```bash
sudo apt-get install -y --no-install-recommends wine64 xvfb
export WINEPREFIX=/path/to/prefix WINEDEBUG=-all DISPLAY=:99
Xvfb :99 -screen 0 1280x800x24 &
wine64 wineboot -i
timeout -s KILL 12 wine64 ./game.exe > run.log 2>&1 </dev/null
grep -iE "page fault|GLAD|Version:|FBO|WARNING" run.log
```

> **함정 2가지**
> 1. `$(...)` 명령 치환으로 출력을 받으면 **자식이 파이프를 잡고 있어 멈춘다.** 파일로 리다이렉트할 것.
> 2. **"프로세스가 살아있다"를 성공으로 판정하면 안 된다.** 크래시하면 wine 디버거가 붙어
>    프로세스가 계속 살아있다. **반드시 로그에서 `page fault`를 확인**해야 한다.
>    (이 검증에서 실제로 RGFW를 한 번 "정상"으로 오판했다.)

### 백엔드 교체 — 크기는 줄지만 검증에 실패했다 (코드 수정 0줄)

raylib은 윈도잉/그래픽 백엔드를 **define으로 교체**할 수 있다. 개조가 아니라 공식 지원 설정이다.
(`src/platforms/` 에 `rcore_desktop_glfw.c`, `rcore_desktop_rgfw.c`, `rcore_desktop_sdl.c` 등 존재)

| 윈도잉 | 그래픽 API | 바이트 | GLFW+GL3.3 대비 |
| --- | --- | ---: | ---: |
| GLFW | GL 3.3 | 502,272 | — |
| GLFW | GL 2.1 | 502,272 | 0 (동일) |
| GLFW | GL 1.1 | 437,760 | −64,512 |
| **RGFW** | **GL 3.3** | **331,776** | **−170,496** |
| RGFW | GL 2.1 | 331,776 | −170,496 |
| **RGFW** | **GL 1.1** | **266,752** | **−235,520 (−47%)** |

**적용법** — `rglfw.c`를 컴파일 목록에서 빼고 define만 바꾼다:
```bash
# GLFW → RGFW
-DPLATFORM_DESKTOP_RGFW      # (기존: -DPLATFORM_DESKTOP)
# 컴파일 파일에서 $S/rglfw.c 제거
```

**트레이드오프**
- **GL 1.1은 셰이더를 잃는다.** 포스트 프로세싱, 팔레트 스왑 셰이더, 블룸 불가.
  셰이더를 안 쓰기로 확정됐다면 공짜로 −65KB.
- **RGFW는 GLFW보다 검증이 덜 됐다.** 게임패드·다중 모니터·전체화면 동작을 반드시 확인할 것.
  (`02-심사기준분석.md`의 전시 적합성 항목 — 게임패드 지원이 걸려 있다)
- **GL 2.1은 GL 3.3과 크기가 완전히 동일**하므로 고를 이유가 없다.

> 🔴 **이 표의 RGFW 행은 크기만 유효하고 실행에 실패했다** (위 실행 검증 결과 참고).
> **채택하지 않는다.** 실제 Windows에서 동작이 확인되면 −170,496 바이트를 회수할 수 있는
> **보류된 기회**로만 남겨둔다.
>
> GL1.1(GLFW 기준 437,760)은 셰이더를 포기하는 대신 −64,512를 주는 별개 카드이며,
> GLFW 위에서는 아직 실행 검증하지 않았다.

### "필요한 부분만 손으로 발췌"가 무의미한 이유

모듈별 오브젝트 크기(링커 정리 전, 트림 config, GL3.3):

| 오브젝트 | 바이트 |
| --- | ---: |
| `raudio.o` | 774,845 |
| `rcore.o` | 742,420 |
| `rglfw.o` | 428,774 |
| `rtextures.o` | 411,912 |
| `rshapes.o` | 66,433 |
| `rtext.o` | 49,080 |
| `utils.o` | 16,537 |
| **합계** | **2,490,001** |
| **→ 최종 exe** | **502,272 (80% 폐기)** |

`-ffunction-sections -fdata-sections -Wl,--gc-sections`가 **안 쓰는 함수를 이미 전부 버린다.**
손으로 코드를 발췌하는 건 링커가 한 일을 사람이 반복하는 것이라 이득이 거의 없다.
남은 502KB는 죽은 코드가 아니라 **실제로 실행되는 코드**다.

**→ 줄이려면 "발췌"가 아니라 "백엔드 교체"(위 항목)나 "기능 포기"여야 한다.**

### 자작 엔진과의 비교 — 얼마나 이득인가

raylib이 번들한 것과 **동일한 버전**의 단일 헤더를 그대로 뽑아 Win32+GDI 위에 직접 조립한 결과:

| 스택 | 바이트 | 증분 |
| --- | ---: | ---: |
| Win32 + GDI 게임 루프 | 57,856 | |
| + stb_image (`STBI_ONLY_PNG`) | 73,728 | **+15,872** |
| + stb_truetype | 93,696 | +19,968 |
| + miniaudio (FLAC/MP3/WAV 디코더 off) | 200,704 | **+107,008** |
| + jar_xm (XM 재생) | **219,136** | +18,432 |

**시사점**
1. **PNG 디코더는 15,872 바이트다.** "자작하면 이미지를 raw로 넣어야 한다"는 것은 사실이 아니다.
   stb_image는 퍼블릭 도메인 단일 헤더라 어디에든 넣을 수 있다.
2. **miniaudio(+107,008)가 자작 스택의 최대 항목이다.** WASAPI를 직접 열면 수 KB로 끝나므로,
   자작으로 간다면 여기가 최대 절감 포인트(→ 전체 ~120KB 가능).
3. **이 219,136에는 GPU 렌더러가 없다.** GDI 블리팅뿐이다.
   알파 블렌딩·회전·스케일·렌더타깃을 **소프트웨어 블리터로 직접 구현**해야 한다.
   도트 게임이면 할 만하고 픽셀이 뭉개지지 않는 장점도 있지만, 며칠짜리 작업이고
   파티클 수천 개 같은 건 CPU로 버겁다.
4. **RGFW+GL1.1(266,752) vs 자작(219,136) = 47,616 바이트 차이.**
   → **자작해서 얻는 실익이 사실상 사라진다.** raylib API를 그대로 쓰면서 비슷한 크기가 나온다.

## 재현 방법

```bash
# 툴체인 (root 불필요, 크로스컴파일 내장)
curl -LO https://ziglang.org/download/0.16.0/zig-x86_64-linux-0.16.0.tar.xz
tar xf zig-x86_64-linux-0.16.0.tar.xz

# raylib 소스
curl -L -o raylib.tar.gz https://github.com/raysan5/raylib/archive/refs/tags/5.5.tar.gz
tar xf raylib.tar.gz

# 트림 config: raylib-5.5/src/config.h 를 복사해 위 40개 옵션을 주석 처리한 뒤
S=raylib-5.5/src

# ★ 권장 구성: RGFW + GL3.3 (331,776 바이트) — rglfw.c 없음에 주의
zig cc -target x86_64-windows-gnu -Os \
  -I$S -I$S/external/glfw/include \
  -DEXTERNAL_CONFIG_FLAGS -include cfg/config.h \
  -DPLATFORM_DESKTOP_RGFW -DGRAPHICS_API_OPENGL_33 \
  -ffunction-sections -fdata-sections -Wl,--gc-sections -s \
  -Wl,--subsystem,windows \
```

## 이 측정의 한계 — 반드시 확인할 것

1. **검증 환경이 Wine이지 실제 Windows가 아니다.**
   - `-Wl,--gc-sections`로 인한 심볼 누락은 없음이 확인됐다 (GLFW 구성 정상 동작).
   - 그러나 **Wine의 OpenGL은 Mesa로 처리**되므로 실제 GPU 드라이버 거동과 다르다.
     **성능은 측정 의미가 없다.**
   - **게임패드·전체화면·다중 모니터는 Wine으로 검증 불가.** 전시 적합성
     (`02-심사기준분석.md`)과 직결되므로 **실제 Windows 확인이 여전히 필요하다.**
   - **RGFW 실패도 Wine 고유 문제일 수 있다** — 실제 Windows에서 재확인 가치가 있다.
2. **툴체인이 MSVC가 아니라 LLVM/MinGW**다. MSVC `/MT /O1 /GL /LTCG`로 빌드하면
   숫자가 다를 수 있다(대체로 비슷하거나 약간 작음). 어느 쪽이든 여유가 크므로 결론은 안 바뀐다.
3. **sokol 83,968바이트는 "화면 클리어"까지만**이다. 스프라이트 배처·폰트·오디오를
   직접 구현하면 raylib에 근접하거나 넘을 수 있다. **작아서 고른다면 직접 구현 비용을 각오할 것.**
4. SDL/LÖVE/Godot 수치는 **공식 배포 바이너리** 기준이다. 소스에서 극단적으로 커스텀 빌드하면
   줄어들지만, 28일 일정에서 시도할 작업이 아니다.

---

5. **자작 스택(219,136)은 "크래시 없음"만 확인됐다.** GDI 기반이라 GL 이슈는 없지만,
   실제 렌더링 품질·성능은 소프트웨어 블리터를 구현해봐야 안다.
6. **라이선스**: raylib은 **zlib/libpng 라이선스**로 개조·발췌·재배포·상업 이용 모두 자유.
   고지만 유지하면 된다. stb_*는 퍼블릭 도메인, miniaudio는 퍼블릭 도메인/MIT-0, jar_xm은 WTFPL/MIT.
   → **`07-제출체크리스트.md`의 "사용 자료 권리 보유 확인" 항목에 라이선스 목록을 정리해둘 것.**

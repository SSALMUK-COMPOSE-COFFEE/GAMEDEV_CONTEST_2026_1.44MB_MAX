# DEFRAG — 게임 기획

확정일: 2026-08-07 (D-28) / 상태: **회색박스 v0 동작 확인**

## 한 문장

> **당신은 디스크 헤드이고, 흩어진 파일 블록을 연속 주소로 이어붙여서, 디스크가 가득 차기 전까지 버틴다.**

## 코어 룰

격자 = 디스크. **한 행이 하나의 트랙**이고, 셀 하나가 섹터다.

1. OS가 `writeInterval`마다 새 파일(블록 2~5개)을 **빈 섹터에 흩뿌려** 쓴다 → 단편화
2. 플레이어는 헤드를 움직여 블록을 **한 번에 하나씩** 집고 놓는다
3. 한 파일의 모든 블록이 **한 행(=트랙) 안에서 연속**되면 `COMPACTED`
   → 블록이 사라지고 **섹터가 비워진다** + 점수 (`size² × 10 × combo`)
4. 파일에는 **수명**이 있다. 제때 정리하지 못하면 **썩어서 배드섹터로 굳는다**
   → 그 섹터는 영구히 사용 불가. **디스크가 영구적으로 좁아진다**
5. OS가 쓸 빈 섹터가 모자라면 → **DISK FULL, 게임오버**

### 이 설계의 두 축

| 축 | 역할 |
| --- | --- |
| **COMPACT → 공간 회수** | 잘하면 보상. 테트리스의 줄 삭제에 해당 |
| **ROT → 공간 영구 손실** | 못하면 처벌. 되돌릴 수 없어 압박이 누적된다 |

이 둘이 없으면 게임이 성립하지 않는다. v0 첫 빌드에서 ROT이 없었더니
디스크가 영영 안 차서 **패배 조건이 죽어 있었다.**

### 파일 크기는 랜덤이고, 색은 크기를 뜻하지 않는다

파일 크기는 생성 시 **2~5칸 중 무작위**로 정해진다. 색은 슬롯 번호(0~7)일 뿐이라
**같은 색이 다음 판에는 다른 크기**로 나온다. 색 = 소속, 크기 = 별개 정보다.

1차 테스트에서 "색마다 개수가 정해진 거냐"는 질문이 나왔다. 즉 플레이어가 색에서
규칙을 찾으려 했다는 뜻이고, 그건 각 파일이 몇 칸짜리인지 화면 어디에도 없었기
때문이다. → **HUD에 파일마다 `크기만큼의 점`을 그린다.** 점 개수 = 채워야 할 칸 수.

> 색이 크기를 고정하게 만드는 안(파랑=항상 2칸)도 가능하지만, 그러면 색이 소속과
> 크기를 동시에 뜻하게 되어 8개 슬롯이 4~5개로 줄고 동시 파일 수가 깎인다. 채택하지 않았다.

### 난이도에 따른 목적지 표시 단계

목적지 슬롯 표시는 **규칙을 가르치고 나면 물러난다.** 표시가 꺼질 때는 배너로
알린다(안 그러면 버그로 읽힌다). 판정은 그 판에서 정리한 파일 수(`compacted`)로 한다.

| 단계 | 조건 | 표시 |
| --- | --- | --- |
| `ASSIST_FULL` | 정리 6개 미만 | 항상 표시 (손에 든 것 / 헤드 아래 / 가장 급한 것) |
| `ASSIST_CARRY_ONLY` | 6~14개 | **블록을 들고 있을 때만** |
| `ASSIST_OFF` | 15개 이상 | 표시 없음. 하단 안내문도 규칙 설명으로 바뀜 |

### 파일 종류 — 코어 메커닉의 파생 변주

`03-기획전략.md`가 허용한 "코어 메커닉 1개 + 파생 변주 2~3개" 항목.
변주가 0개일 때는 3분은 재밌어도 15분을 버틸 판단거리가 없었다.

| 종류 | 등장 | 규칙 | 표시 |
| --- | --- | --- | --- |
| **NORMAL** | 항상 | 기본 | — |
| **VOLATILE** | 3개 정리 후, 22% | **수명 절반, 점수 3배.** 먼저 칠까 버릴까의 판단 | 블록 중앙에 흰 사각형 점멸, HUD 점에 흰 마크 |
| **PINNED** | 8개 정리 후, 25% (3칸 이상) | **블록 하나가 못 움직인다.** 그 블록을 포함하도록 배치를 짜야 한다 | 어두운 테두리 + 가운데 점, HUD 점 아래 밑줄 |

목적지 슬롯 계산이 PINNED를 자동으로 반영한다 — 고정 블록을 포함하는 창만 후보가 된다.
고정 블록을 집으려 하면 거부음 + 짧은 흔들림으로 알린다.

> **"잠긴 파일"(N초간 못 옮김)은 채택하지 않았다.** 기다림은 판단이 아니라 대기라
> 재미가 붙지 않는다. 같은 "제약" 역할을 PINNED가 대기 없이 수행한다.

파일 최대 크기도 진행에 따라 커진다 (5칸 → 10개 정리 시 6칸 → 20개 시 7칸).

### SCANDISK — 배드섹터 회복

부패가 쌓이기만 하고 절대 줄지 않아서 **모든 판이 똑같이 끝났다.** 천천히 조여오다
죽는 것 외에 후반의 목표가 없었고 역전 수단이 전혀 없었다.

- COMPACT할 때마다 정리한 칸 수만큼 SCANDISK 게이지가 찬다
- 14칸이 차면 **배드섹터를 앞에서부터 최대 3개 되살린다** (디스크 선두부터 훑는
  실제 scandisk의 거동)
- 회복 칸은 초록으로 쓸려나가며 비워지고, 배너와 전용 효과음으로 알린다

이제 잘하면 디스크가 **넓어진다.** 후반에 추격할 목표가 생겼다.

### 동시 파일 수 = 팔레트 색 수 (8)

두 파일이 같은 색이면 플레이어가 소속을 구분할 수 없다.
그래서 **`MAX_FILES` = 팔레트 8색**으로 못 박았다. 난이도는 파일 수가 아니라
**쓰기 주기 단축 + 수명 단축 + 배드섹터 누적**으로 올린다.

## 첫 60초 시나리오

```
0s   타이틀에서 SPACE → 즉시 격자. 로딩 없음
3s   헤드 이동/집기 성공. 블록 하나를 옆 칸에 붙임
8s   같은 색 2개가 붙자 링크 마커가 그려짐 → "이어붙이는 거구나"
15s  첫 COMPACT. 화면 흔들림 + 섹터가 비워짐 → "치우면 공간이 생긴다"
25s  파일 수명 게이지가 처음 빨개짐 → "시간 제한이 있구나"
35s  방치한 파일이 배드섹터로 굳음 → "저건 영구 손실이다"
50s  콤보 배수 발견. 연속 정리가 점수를 폭발시킴
60s  FREE 게이지가 처음 눈에 들어옴 → 장기 목표 인지
```

### 일시정지 중에는 판을 가린다

시간 압박이 핵심인 게임에서 일시정지는 **공짜 사고 시간**이 된다. 멈춰놓고 배치를
분석하면 점수 어택이 무의미해지므로, 일시정지 중에는 블록·목적지 슬롯·헤드·파티클을
전부 숨기고 빈 섹터 격자만 남긴다.

창 포커스를 잃으면 자동으로 일시정지된다. 단 **매 프레임이 아니라 포커스가 빠지는
순간에만** 건다 — 계속 검사하면 포커스 감지가 안 되는 환경에서 P를 눌러도 다음
프레임에 다시 멈춰 영영 못 푸는 상태가 된다.

## 1차 플레이테스트 (2026-08-07, D-28) — **"뭘 해야 할지 모르겠다"**

첫 플레이 피드백이 **목표 불명확**이었다. 완성도·재미 이전에 게임이 성립하지 않는
문제라 즉시 대응했다. 원인은 세 가지였고 전부 v0의 구조적 결함이었다.

| 원인 | 대응 |
| --- | --- |
| **목적지가 화면에 없었다.** 플레이어가 row-major 순서를 머릿속으로 상상해야 했다 | **목적지 슬롯을 격자에 직접 그린다.** 손에 든 파일 / 헤드 아래 파일 / (없으면) 수명이 가장 급한 파일의 목표 위치를 흰 테두리로 점멸 |
| **행 넘김(wrap)이 시각적으로 말이 안 됐다.** 오른쪽 끝 블록의 다음 주소가 화면 반대편 다음 줄이라 목적지가 엉뚱한 곳에 떴다 | **연속을 한 행(트랙) 안으로 제한.** 테마도 더 정확해짐 — 행 = 트랙, 조각모음 = 파일을 한 트랙에 몰기 |
| **판이 너무 비어 막막했다.** 24×14=336칸에 블록 십여 개, 시작하자마자 파일 3개 | **격자 18×10=180 (셀 40px)로 축소 + 2블록짜리 파일 1개로 시작.** 첫 성공까지의 거리를 짧게 |

추가로 상시 안내문(`CARRY EACH BLOCK INTO THE GLOWING SLOTS OF ITS OWN COLOUR`)을
격자 아래에 고정 배치했다. 심사자는 60초를 주고 매뉴얼을 읽지 않는다.

> **교훈: 규칙이 논리적으로 옳은 것과 화면에서 읽히는 것은 전혀 다른 문제다.**
> 선형 주소 연속은 정확한 defrag 모델이었지만 2D 격자에서 아무도 못 읽는다.

## 게임필 (2026-08-07, D-28)

`02-심사기준분석.md`가 지목한 항목 — **용량을 거의 안 먹으면서 체감 퀄리티를 가장
크게 올린다.** 전부 절차적이라 에셋 0개, 실측 증가분 **+1,536바이트**.

| 요소 | 내용 |
| --- | --- |
| **헤드 보간** | 칸 사이를 순간이동하지 않고 미끄러진다 (초당 22 비율 lerp) |
| **COMPACT 쓸어내기** | 한꺼번에 번쩍이 아니라 셀마다 0.07초씩 밀려 왼→오른쪽으로 지나간다. 헤드가 트랙을 훑는 것처럼 읽힌다 |
| **히트스톱** | COMPACT 시 `0.05 + 크기×0.012`초, 부패 시 `0.10`초 시뮬레이션 정지. 그리기는 계속되어 정지 프레임이 그대로 보인다 |
| **파티클** | 160개 링 버퍼. 블록을 놓을 때 / 섹터가 비워질 때 / 부패할 때. 오래된 것을 재사용해 큰 COMPACT가 작은 것보다 약해 보이지 않게 한다 |
| **점수 팝업** | COMPACT 위치에서 `+점수`가 떠오르며 사라진다 |
| **화면 흔들림** | COMPACT은 크기 비례, 부패는 더 크게 |

> **부패의 히트스톱(0.10초)을 COMPACT보다 길게 잡았다.** 섹터를 잃는 쪽이 얻는 쪽보다
> 무겁게 느껴져야 한다.

## 사운드 (2026-08-07, D-28) — 전부 절차적, 파일 0개

`05-용량예산.md`가 "최상" 등급으로 찍은 **런타임 절차적 합성**을 채택했다.
오디오 파일도 트래커 모듈도 없다. 파형을 코드가 만든다.

### SFX 9종

`renderTone()`이 주파수 스윕 + 제곱 감쇠 엔벨로프로 파형을 만들어
`LoadSoundFromWave()`에 넘긴다. 오실레이터는 사각파 / 삼각파 / 노이즈 3종뿐이다.

| 소리 | 파형 |
| --- | --- |
| 집기 | 사각파 520→900Hz 상승, 0.07초 |
| 놓기 | 사각파 420→200Hz 하강, 0.06초 |
| COMPACT ×4 | 3음 아르페지오. **콤보 단계마다 4도씩 올라간다** |
| 부패 | 노이즈 900→120Hz, 0.45초 |
| 게임오버 | 삼각파 330→60Hz, 1.1초 |
| 표시 단계 변경 | 사각파 700→1000Hz |

### BGM

`SetAudioStreamCallback`으로 오디오 스레드에서 **실시간 합성**한다. 버퍼에
곡을 미리 렌더링하지 않으므로 메모리도 거의 안 쓴다.

- 132 BPM, 16분음표 그리드, 4마디 루프 (Am–F–C–G)
- 사각파 리드 아르페지오 + 삼각파 베이스 + 노이즈 하이햇
- 각 성부는 개별 감쇠 엔벨로프 (리드 7/s, 베이스 4/s, 하이햇 45/s)

### 오디오 장치가 없을 때

`IsAudioDeviceReady()`가 실패하면 `audioReady = 0`이 되어 사운드를 아예 로드하지
않고 `playSfx()`도 no-op이 된다. **소리 없이 정상 동작한다.**
사운드카드가 없는 심사자 환경이나 VM에서도 크래시하지 않는다.

`M` 키로 음소거 토글 (`02-심사기준분석.md`의 "사운드 On/Off 토글" 항목).

## 전시 적합성 (2026-08-07, D-28)

`02-심사기준분석.md`의 "전시 친화적 설계" 항목 처리. 수상작은 2P GAME ARCADE
전시회에 전시될 수 있으므로, 심사자는 무의식적으로 "부스에 놓을 수 있나"를 본다.

### 어트랙트 모드 / 자동 리셋

무입력이 이어지면 타이틀로 돌아간다. 플레이 중 30초, 게임오버 화면 15초.
다음 관람객이 **항상 처음부터** 시작하게 된다.

**마지막 5초에 경고를 띄운다** (`NO INPUT - RETURNING TO TITLE IN n`).
예고 없이 튕기면 고장으로 읽힌다.

타이틀 화면에는 배경에 어트랙트 애니메이션이 돈다 — 흩어진 블록이 한 행으로
모여 사라지는 6초 루프 + 스캔 바. 그 위에 어두운 막을 씌워 글자 가독성을 지킨다.

### 전체화면 / 창 리사이즈

단순 `ToggleFullscreen()`으로는 안 된다. 모든 좌표가 960×660 고정이라 전체화면에서
화면 좌상단에 원본 크기로 쪼그라든다.

**해결: 960×660 렌더 텍스처에 그린 뒤 창 크기에 맞춰 비율 유지 스케일 + 레터박스.**
`TEXTURE_FILTER_POINT`로 픽셀이 뭉개지지 않게 한다. 이 방식이 전체화면과

## 빌드

```bash
tools/bootstrap.sh  # 머신당 1회. 호스트에 맞는 zig 0.16.0 + raylib 5.5 → vendor/
./build.sh          # 기본값 = both. 호스트 개발 빌드 + 제출용 exe
./build.sh win      # dist-win/defrag.exe — 심사 대상. 용량 게이트 자동 실행
./build.sh mac      # dist-mac/defrag — 개발용. 맥에서 직접 실행할 것
./build.sh linux    # dist-dev/defrag — 개발용 (X11 개발 헤더 필요)
```

### 산출물은 폴더 2개, 파일 2개

```
dist-win/defrag.exe   ← 제출물. 이 폴더에 이 파일 하나뿐 (동봉 DLL 0개)
dist-mac/defrag       ← 개발용. 제출과 무관
```

**하나의 파일이 양쪽에서 도는 게 아니다.** 타깃별로 별개의 바이너리다.
제출은 `dist-win/`만 압축한다 — `01-규칙원문.md`의 "압축 해제 후 폴더 전체 합계"
기준이므로 개발용 산출물이 섞여 들어가면 그대로 용량에 합산된다.

`both`에서 개발 빌드가 실패해도 **제출 빌드는 계속 진행**된다(경고만 출력).
플랫폼 SDK 헤더가 없는 머신 때문에 심사 대상 빌드가 막히면 안 되기 때문이다.

- `vendor/`는 git에 올리지 않는다. 새 머신에서는 `bootstrap.sh`부터.
- **맥 빌드는 크로스컴파일이 아니라 맥에서 네이티브로 돌린다.** macOS SDK가 필요하고,
  `rglfw.c`는 Cocoa `.m` 소스를 include하므로 `-x objective-c`로 따로 컴파일한다.
  링커도 GNU ld가 아니라 Apple ld라 `--gc-sections` 대신 `-dead_strip`을 쓴다.
- Windows 빌드만 zig(크로스컴파일)를 쓰고, 나머지는 시스템 컴파일러를 쓴다.
